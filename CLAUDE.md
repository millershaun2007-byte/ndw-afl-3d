# ndw-afl-3d (Mount Duneed Cats Footy)

Unity WebGL game. Deployed build lives at `gs://ndw-game-builds/afl3d/` (public GCS bucket, served directly — see "CI/CD pipeline" below). **Not currently embedded in the main NeuroDinoWorld app** — its card was deliberately pulled from `www/js/ndw-activities.ts`'s Creative/Aussie Games grid on 2026-08-20 after a live production black-screen report and a list of known-unfinished mechanics (see "Known open issues" below). The `'afl'` activity id still has a placeholder fallback message wired in the main app in case the id is ever reached via a stale deep-link — this is intentional, not a bug.

**Direct link to the current live build**: https://storage.googleapis.com/ndw-game-builds/afl3d/index.html

## Before touching gameplay code, read this section and the "Known open issues" section below

This repo has a documented recurring failure mode, named explicitly in earlier revisions of this file: **one fact about the world written down in two places that then drift apart.** Every real bug fixed in the 2026-08-21 session (see "2026-08-21 session" below) was exactly this pattern — ball position vs. kicker position, a camera pivot vs. the value it should have used, a direction flip that cancelled a possession flip. Before tuning anything, ask whether the number you're about to change has a twin somewhere else that also needs to move, and before assuming a visual bug is a camera problem, print and compare the actual world-space positions/heights involved rather than guessing from what's on screen.

## CI/CD pipeline (fixed 2026-08-21 — was broken for days before this)

`.github/workflows/build-deploy.yml` builds and deploys automatically on every push to `main`. This took real, multi-stage debugging to get working — read the workflow file's own inline comments for the full history, but the short version:

1. **Unity Hub install** (`RageAgainstThePixel/unity-setup@v2`) hard-codes the expected Hub path at `/opt/unityhub/unityhub`, but the modern `unityhub` Debian package installs its whole app tree (binary, `resources/app.asar`, and the separate `UnityLicensingClient_V1` directory a later step needs) under `/usr/lib/unityhub/`, with `/usr/bin/unityhub` just a symlink into it. Fixed with **one directory-level symlink** (`/opt/unityhub -> /usr/lib/unityhub`) rather than symlinking individual files one at a time — an early attempt at fixing individual files repeatedly missed a *different* file each of 3 different downstream steps needed.
2. **The build itself no longer uses `game-ci/unity-builder`'s Docker container.** That container is a separate environment from the bare runner the license activates on, so it never saw the activated license (confirmed via a real failure reaching the build step: "Missing Unity License File and no Serial was found" — `unity-builder`'s own activation script only supports a classic `UNITY_SERIAL` or a floating license server, neither applicable here). The workflow now installs the **real Editor + WebGL module** (not just Hub) via a second `unity-setup@v2` call, and invokes `Unity -batchmode -quit -nographics -executeMethod MainBuildScript.PerformWebGLBuild` **directly on the same runner**, in the same environment the license activated in.
3. Deploys the output via `gcloud storage rsync build/WebGL gs://ndw-game-builds/afl3d/` using keyless Workload Identity Federation (no long-lived GCP key in the repo).

**Total run time is ~25 minutes**, almost entirely the one-time-per-run Editor download (the cache-save step hasn't successfully cached across runs yet — `[install-state] downloads-store` cache save has failed with "invalid" warnings every run so far; worth investigating if run time matters, not yet done).

**A local build is always available as a faster fallback for iteration**: Unity 6000.5.7f1 is installed locally on this Mac (`/Applications/Unity/Hub/Editor/6000.5.7f1-arm64/Unity.app/Contents/MacOS/Unity`), already licensed. `Unity -batchmode -quit -nographics -projectPath . -executeMethod MainBuildScript.PerformWebGLBuild` builds in ~25s locally, then `gcloud storage rsync Build/WebGL gs://ndw-game-builds/afl3d/ --recursive --delete-unmatched-destination-objects` deploys it directly. **Real hazard confirmed this session: if you push a commit (triggering the ~25-minute CI pipeline) and then also build+deploy locally for faster verification, the CI run can finish LATER and silently overwrite your local deploy with older code** — happened multiple times on 2026-08-21. Always check `gh run list --repo millershaun2007-byte/ndw-afl-3d --limit 3` for any `in_progress` run before trusting a local deploy's timestamp, and `gh run cancel <id>` any stray one before redeploying locally.

## 2026-08-21 session — kick-out, second contest, clearance chain

Starting point: the game already had a working 5-beat chain for a single centre-bounce round (ruck tap → rover run+kick → mark contest → shot at goal), confirmed and stable from earlier sessions. This session extended it with what happens after a **spoiled** mark, working through real, load-bearing bugs at each step — all found by tracing actual coordinates/values, not by guessing from symptoms, after several early guesses that fixed real-but-secondary issues without resolving the reported symptom.

**Current shipped state** (`Day1RuckContest.cs`):
- A spoiled mark on the very first (centre-bounce) contest → **rushed behind** (ball kicks through the defending team's own behind posts for 1 point) → that team's own player **kicks out from fullback** (real procedural leg-kick animation, ball genuinely tracks the boot bone, dedicated wide camera framing the actual ~12-unit traverse) → the **recovering team gets one more contest** (their own rover run + kick + mark attempt, reusing the exact same `TapBallAway`/`KickAway` machinery the centre bounce uses — no new mechanic, no re-tuned jump timing).
- That second contest **currently stops at a confirmed mark or a capped spoil**, deliberately — does not yet chain into a shot at goal or a third contest. This is an explicit, temporary scope decision (Shaun, 2026-08-21: "we literally need to take one step at a time") to let the mark itself get verified in isolation before building what happens after it. `maxChainDepth = 1` in the same file is the actual bound if this gets extended again — a spoil past the first contest currently ends the round honestly ("Time's up — turnover!") rather than chaining further.
- A team's attacking direction is a **fixed property of the team**, not of who currently has the ball — Croc always attacks +Z, Roo always -Z, for the whole game. `TapBallAway`'s `crocsInPossession` parameter (deliberately renamed from `crocWins` once the function became re-entrant — the old name described a one-off event, not the ongoing state it now tracks) is the only thing direction derives from; there is no separate direction-override parameter anymore (one existed, `reverseDirection`, and was found to silently cancel the direction implied by a possession change — removed entirely rather than patched).

**Real bugs found and fixed this session, in the order discovered** (each confirmed via automated Playwright screenshot passes across multiple full rounds before being called done, then further corrected when live playtest feedback still didn't match):
1. Ball frozen at the previous contest's peak jump height, never reset to ground level before the rushed-behind/kick-out sequence — visually read as "the ball floats near the top of the goal posts."
2. `CutCameraForKick`'s pivot formula (`zDir * (goalZ - 5)`) is only valid for a contest heading into a goal from nearby — reused unmodified for the kick-out (which travels the *entire* ground length), so most of the flight was off-camera. Fixed with a dedicated wide shot (`CutCameraForKickOut`) sized for that specific traverse.
3. The kicker's own standing position (after `RunToZ`, which only ever moves Z) landed almost exactly between two goal posts, so the mark/kick-out close-up camera looked straight through a post. Fixed by sliding clear of the post cluster before the close-up cuts in, plus a mirrored `CutCameraToMarkCloseup(subject, side)` overload for the -X spawn side (the original, fixed +X-offset version stayed in place for the mark beat that already used it and was already signed off — only the newly-added chained beats needed the mirrored version).
4. The kick-out's own camera pivot passed `rover.position.z` (the *input* to `peakZ`) instead of `peakZ` itself — aimed 8 units short of where the contest actually happens on every chained contest.
5. Every chain hop advances the ball ~14 units downfield with no bounds check against the field's real half-length (`goalZ`) — after 1-2 hops this could already exceed the field, putting a camera pivot derived from that position somewhere absurd (confirmed via screenshot: camera pointed almost entirely at the sky). Clamped at three levels that each independently compound the drift (rover's position after `RunStraight`, `peakZ`, and `KickAway`'s own `kickEnd`).
6. **The real direction bug**: `reverseDirection: true` on the kick-out's chain call, combined with the `crocsInPossession` flip that already happens on a possession change, cancelled out — the recovering team kept running toward the goal they'd just been defending instead of their own. This was the actual cause of "all over the shop" / "the defence works it up towards the other goal" — the earlier five fixes were all real but secondary. Confirmed via a real diagnostic printing live captured coordinates (`crocsIn=True dir=1 rvZ=-2 pkZ=6` for one real instance) before being called fixed, not from reasoning about the geometry alone — reasoning about it got it wrong more than once.

**Verification standard used throughout**: per this repo's own established rule, "it builds," "it deploys," and "a screenshot pass has seen it" are three different, explicitly weaker claims than "a human has actually played it." Every fix above was verified via a real deployed build + an automated Playwright screenshot pass across multiple full rounds (both spawn sides, multiple outcome types) before being reported as fixed — but every report to Shaun was explicit that this is not the same as his own playtest, and several fixes that passed the automated check still needed correction once he actually played it. Don't skip the automated check (it catches real, confirmable regressions fast), but don't mistake it for the human confirmation this repo's definition of done actually requires either.

Same fix pattern, not yet applied there.

## Definition of done (standing rule, unchanged, repeat it every session)

This game is not done when it builds, not when it deploys, and not when the console is clean. It is done when a person plays it for real, without being coached, and the thing being claimed as fixed actually reads correctly on screen to them. Say explicitly which of the four claims (builds / deploys / screenshot-verified / human-played) applies to any specific piece of work — they are not interchangeable, and conflating them is exactly how a broken build shipped live before.
